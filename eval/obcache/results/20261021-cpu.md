# OBCache CPU 성능 평가 — LongBench 제외

**이번 CPU 포팅에서는 GPU에서 효율적으로 처리하는 점수 계산의 비용을 충분히
줄이지 못했고, 전체 추론 지연시간 개선을 얻지 못했다.** 전체 latency는 Linux
+153.3%, native Windows +45.5%였으며 sampled peak memory는 거의 같았다.
논문의 A100 GPU 결과만으로 온디바이스 CPU에서도 같은 시간 절감을 기대할 근거는 없다.
이 결과는 현재 포팅·모델·실험 조건에 대한 결과이며, 모든 CPU에서 OBCache가
효과 없다는 결론으로 일반화하지 않는다. 실제 KV 저장소 축소도 아직 구현되지 않았다.

독립 main baseline `7d14d001`과 OBCache-K를 Linux(WSL2) 및 native Windows에서 비교했다.
각 OS에서 입력 512/2048/4096별 baseline·방법론 각각 latency 3회와 memory 3회를 새로 실행했다.
총 72개 본 측정이며, 실제 모델 기능 확인 4개와 작은 deterministic 모델 검사는 통계에서 제외했다.

Qwen3-0.6B, FP32 weights/activations, FP16-bit UINT16 KV, batch 1,
capacity 4225, 요청 decode 128, NNTR/OMP 4 threads, OpenBLAS 1 thread.
OBCache는 uniform budget 256/window 64/kernel 5, key score 및 GQA pre_redc를 사용한다.
성능 부하용 반복 token 입력이며 원래 sampling/EOS 설정을 유지했다.

### Linux (WSL2)

Baseline 3회·OBCache 3회 평균; latency와 memory는 별도 프로세스.

| 입력 tokens | Baseline latency (s) | OBCache latency (s) | Latency 변화 | Baseline peak memory (MiB) | OBCache peak memory (MiB) | Memory 변화 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 512 | 40.453 | 75.168 | +85.8% | 2,872.7 | 2,873.9 | +0.0% |
| 2048 | 74.350 | 219.448 | +195.2% | 2,965.4 | 2,969.7 | +0.1% |
| 4096 | 176.685 | 443.692 | +151.1% | 3,088.8 | 3,089.9 | +0.0% |

입력별 평균에 같은 가중치를 준 전체 변화: latency +153.3%, peak memory +0.1%.

메모리: 원본 mem_usage.sh의 모델 PID smaps RSS 표본 최대. OS peak와 구분합니다.

실제 decode 수: `{"512": {"baseline": [128], "obcache": [128]}, "2048": {"baseline": [128], "obcache": [128]}, "4096": {"baseline": [128], "obcache": [128]}}`. EOS로 작업량이 다르면 동일 작업량의 speedup으로 해석하지 않습니다.

### Windows native

Baseline 3회·OBCache 3회 평균; latency와 memory는 별도 프로세스.

| 입력 tokens | Baseline latency (s) | OBCache latency (s) | Latency 변화 | Baseline peak memory (MiB) | OBCache peak memory (MiB) | Memory 변화 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 512 | 67.696 | 83.829 | +23.8% | 2,900.3 | 2,899.1 | -0.0% |
| 2048 | 161.407 | 242.165 | +50.0% | 2,956.4 | 2,956.6 | +0.0% |
| 4096 | 367.303 | 541.915 | +47.5% | 3,082.4 | 3,086.5 | +0.1% |

입력별 평균에 같은 가중치를 준 전체 변화: latency +45.5%, peak memory +0.0%.

메모리: PSAPI current Working Set, 50 ms 표본 최대. OS peak와 구분합니다.

실제 decode 수: `{"512": {"baseline": [128], "obcache": [128]}, "2048": {"baseline": [128], "obcache": [128]}, "4096": {"baseline": [128], "obcache": [128]}}`. EOS로 작업량이 다르면 동일 작업량의 speedup으로 해석하지 않습니다.

latency는 로딩을 제외한 CLI `total:`이며, memory는 로딩·prefill을 포함한
프로세스 생애의 표본 최대다. Linux는 원본 mem_usage.sh로 모델 PID의 smaps RSS를
약 1초 sleep으로 읽고, Windows는 PSAPI current Working Set을 약 50ms sleep으로 읽었다.
API 조회·로그 기록 시간이 추가되며, 표본 사이의 순간 peak는 놓칠 수 있다.
OS peak는 별도 JSON에 보존했으며 주 지표와 혼용하지 않았다.
기존 helper의 보조 os_peak_rss_kib 필드는 CLI peak memory(RssAnon+accel)를 읽었다.
공개 JSON에서는 원본 로그의 Max Resident Set Size로 실제 OS peak를 재파싱하고,
기존 CLI 값과 원본 manifest를 별도로 보존했다. 주 latency·sampled RSS 수치는 변경하지 않았다.
CPU affinity는 Linux 0,2,4,6, Windows 미고정이다. 온도·주파수 제어는 하지 않았다.

K/V allocation 크기는 유지한다. Prefill 후 cache를 압축하고 decode 토큰을 추가하며,
추가 점수 계산과 CPU 구현 비용도 latency에 포함한다. 출력 품질은 이 성능 입력으로 판단하지 않는다.
**사용자 요청에 따라 LongBench는 실행하지 않았으며 품질 점수는 없다.**

Linux는 GCC 13.3.0, Windows는 MinGW GCC 13.2.0의 CPU release 빌드다.
테스트 옵션을 끈 별도 측정 빌드를 사용했다. 변경 없는 main core 라이브러리는 소스·헤더·
컴파일 옵션·툴체인 일치를 검증한 뒤 재사용했고, OBCache CausalLM 코드는 새로 빌드했다.
Windows는 baseline과 같은 task-local GNU 호환 설정 및 main-return exit adapter를 적용했다.
모델/지역 객체 정리와 main 반환 후 종료하며 DLL global destructor 구간은 제외한다.
전체 플랫폼 빌드 매트릭스 CI 통과를 주장하지 않는다.

Linux OBCache 12개(positive 6/negative 6)·기존 Qwen3 6개 모델 테스트와 KVCacheManager 20개 테스트가 통과했다.
양 OS의 작은 모델 off/zero/uncompressed/compressed 및 8-step decode 검사를 통과했다.
모든 본 측정의 raw 로그, activation marker, 실제 token 수, memory 표본과 hash를 재검증했다.
개별 trial, 표본 SD, 프로토콜, 소스·실행 파일·라이브러리 출처는 동명 JSON에 기록했다.
원본 로그와 빌드·검증 기록은 git에서 제외된 `build/validation/obcache-run/`에 보존했다.

### 논문 GPU 실험과 CPU 포팅의 차이

논문 v4는 A100-80GB, BF16, LLaMA-3.1-8B/Qwen2.5-7B 및
PyTorch/KVPress·FlashAttention-2 환경을 사용한다. 공식 OBCache-K 코드는
V/O의 제곱합을 재사용하고 내적을 텐서 행렬 연산으로 처리한다. 현재 포팅은
FP32 CPU 추론에서 점수 계산을 직렬 double 반복문으로 수행하며, Tensor의
타입·폭·포인터 조회와 scalar half→float 변환을 원소마다 반복한다.
논문도 선택한 query의 attention을 재계산하므로, 재계산 자체가 구현 차이는 아니다.
[논문 설정·효율성 평가](https://arxiv.org/html/2510.07651v4),
[고정 revision의 공식 점수 코드](https://github.com/DreamSoul-AI/OBCache/blob/189ffadd7b2f29eaf311e67f39dbf2a26f5f4dd3/kvpress/presses/obcache_press.py#L146)

논문의 효율성 평가에는 TTFT와 동적 score/eviction을 포함한 512-token decode,
batch 1·4가 포함된다. 이번 평가는 static prefill 압축 후 128-step decode,
batch 1이며, 입력도 실제 품질 평가 대신 반복 token 부하다. 하드웨어뿐 아니라
모델·정밀도·정책·작업량·메모리 지표가 달라 논문과 동일한 speedup 비교가 아니다.
GPU에서 보고한 추가 비용이 작다는 결과는 온디바이스 CPU에서 검증된 결과가 아니다.

### 기존 본 측정의 prefill/decode 분해

4096-token 입력의 3회 평균이다. 아래 값은 새 측정이 아니라 원본 trial의
CLI prefill/generation timer를 별도로 집계한 것이다.

| OS | Baseline prefill (s) | OBCache prefill (s) | Baseline decode 128회 (s) | OBCache decode 128회 (s) |
| --- | ---: | ---: | ---: | ---: |
| Linux (WSL2) | 97.548 | 413.738 | 78.723 | 29.401 |
| Windows native | 276.889 | 502.032 | 90.196 | 39.614 |

Decode는 빨라졌지만 prefill 증가가 이를 초과했다. 전체 latency에 대한 개선은 없었다.

### 이미 수집한 Linux 원인 진단

이 보충은 기존 진단 기록을 정리한 것으로, 문서 업데이트를 위해 새 실험을 실행하지 않았다.
실제 4096-token 입력을 별도 계측 라이브러리로 실행한 뒤 **5/28개 레이어 완료 시
의도적으로 중단**했다. 따라서 이 실행은 정상 완료된 전체 추론 trial이 아니며,
본 측정 72회에 포함하지 않는다. 완료된 5개 레이어의 추가 작업은 다음과 같다.

| OBCache 추가 작업 | 5개 레이어 합계 (s) |
| --- | ---: |
| 점수 누적: GQA 집계·O 계산·prefix 중요도 | 112.108 |
| Attention 재계산·softmax | 1.245 |
| Query/score 버퍼 준비 | 0.037 |
| 선택·pooling·K/V 이동 | 0.011 |

점수 누적은 계측한 OBCache 추가 작업 시간의 **98.85%**였다. 이는 모델 전체
prefill 시간의 98.85%라는 뜻이 아니며, 원래 3회 평균의 정확한 비용 분해도 아니다.
현재 4K/64-window key-score 경로의 값 읽기·scalar half 변환 호출 수는 코드상
28층 합계 약 148.6억 회다. GCC 진단에서도 해당 반복문의 벡터화 실패를 확인했다.

같은 UINT16 half-bit V와 A/Z를 사용한 합성 kernel 진단은 관측 query **8행**,
sequence 4096, Q heads 16/KV heads 8, dim 128, 단일 점수 계산 thread에서 수행했다.

| 점수 계산 방식 | 평균 (s), n=3 |
| --- | ---: |
| 원본 accumulator | 1.818 |
| Tensor 접근·key 모드 선택을 반복문 밖으로 이동 | 1.127 |
| 위 처리 + V를 한 번 변환해 재사용 | 0.278 |

이 입력에서 최종 점수의 최대 절대 차이는 0이었다. 약 6.54배는 **합성 점수 계산부의
차이**로, 전체 모델의 개선율이나 논문 정확도 재현 결과가 아니다. V 변환 사본의
생성 시간도 포함했지만 한 레이어에 16 MiB 임시 공간을 추가하므로, 메모리 최적화로
적용된 수정도 아니다. Windows에는 추가 계측을 하지 않았으며 이 비율을 대입하지 않는다.
개별 진단 trial·표본 SD·원본 hash는 [별도 진단 JSON](20261021-cpu-diagnosis.json)에 보존했다.
원본 진단 소스·로그·명령은 로컬 `build/validation/obcache-diagnosis/`에 보존했다.

### 구현 및 해석의 미완료 범위

- **실제 저장소:** 현재는 고정 용량 버퍼 내부에서 K/V를 이동할 뿐, 작은 저장소로
  교체·재바인딩·기존 참조 해제를 구현하지 않았다. 메모리가 거의 같은 것은 이 구현
  선택의 결과이며 CPU의 근본적인 한계로 해석하지 않는다.
- **논문 수식:** 논문 v4 Appendix A.5는 query head별 점수를 KV group에서 합산한다.
  현재는 공식 코드 기본값 `pre_redc`를 따라 A/Z를 먼저 평균내므로 선택 토큰이 달라질 수 있다.
  동일 Q/K/V에서 논문 기준 점수·top-k를 대조하는 검증은 아직 없다.
- **실용성:** 이식된 점수 계산의 비효율과 CPU/GPU 실행 환경 차이가 함께 존재한다.
  개선한 CPU 구현의 전체 속도 이득이나 온디바이스 실용성을 입증한 상태가 아니다.
- **후속 작업:** 실제 KV 저장소 축소, 논문 GQA 정합성, 계산 재사용·행렬 연산 적용은
  [수정 계획](../implementation-plan.md)에만 포함되어 있다. 현재 제품 코드에 적용하지 않았다.

기존 성능 JSON은 평가 시점의 소스·문서 hash와 72개 본 측정을 고정해 보존한다.
이 문서 보충과 진단 요약은 기존 측정 수치 또는 평가 바이너리를 변경하지 않는다.
