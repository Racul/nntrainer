# OBCache CPU 성능 평가 — LongBench 제외

독립 main baseline `7d14d001`과 OBCache-K를 Linux(WSL2) 및 native Windows에서 비교했다.
각 OS에서 입력 512/2048/4096별 baseline·방법론 각각 latency 3회와 memory 3회를 새로 실행했다.
총 72개 본 측정이며, 실제 모델 기능 확인 4개와 작은 deterministic 모델 검사는 통계에서 제외했다.

Qwen3-0.6B, FP32 weights/activations, FP16-bit UINT16 KV, batch 1,
capacity 4225, 요청 decode 128, NNTR/OMP 4 threads, OpenBLAS 1 thread.
OBCache는 uniform budget 256/window 64/kernel 5, key score 및 GQA pre_redc를 사용한다.
성능 부하용 반복 token 입력이며 원래 sampling/EOS 설정을 유지했다.

### Linux (WSL2)

Baseline 3회·OBCache 3회 평균; latency와 memory는 별도 프로세스.

| 입력 tokens | Baseline latency (s) | OBCache latency (s) | Latency 변화 | Baseline peak memory (MiB) | OBCache peak memory (MiB) | Memory 변화 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 512 | 40.453 | 75.168 | +85.8% | 2,872.7 | 2,873.9 | +0.0% |
| 2048 | 74.350 | 219.448 | +195.2% | 2,965.4 | 2,969.7 | +0.1% |
| 4096 | 176.685 | 443.692 | +151.1% | 3,088.8 | 3,089.9 | +0.0% |

입력별 평균에 같은 가중치를 준 전체 변화: latency +153.3%, peak memory +0.1%.

메모리: 원본 mem_usage.sh의 모델 PID smaps RSS 표본 최대. OS peak와 구분합니다.

실제 decode 수: `{"512": {"baseline": [128], "obcache": [128]}, "2048": {"baseline": [128], "obcache": [128]}, "4096": {"baseline": [128], "obcache": [128]}}`. EOS로 작업량이 다르면 동일 작업량의 speedup으로 해석하지 않습니다.

### Windows native

Baseline 3회·OBCache 3회 평균; latency와 memory는 별도 프로세스.

| 입력 tokens | Baseline latency (s) | OBCache latency (s) | Latency 변화 | Baseline peak memory (MiB) | OBCache peak memory (MiB) | Memory 변화 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 512 | 67.696 | 83.829 | +23.8% | 2,900.3 | 2,899.1 | -0.0% |
| 2048 | 161.407 | 242.165 | +50.0% | 2,956.4 | 2,956.6 | +0.0% |
| 4096 | 367.303 | 541.915 | +47.5% | 3,082.4 | 3,086.5 | +0.1% |

입력별 평균에 같은 가중치를 준 전체 변화: latency +45.5%, peak memory +0.0%.

메모리: PSAPI current Working Set, 50 ms 표본 최대. OS peak와 구분합니다.

실제 decode 수: `{"512": {"baseline": [128], "obcache": [128]}, "2048": {"baseline": [128], "obcache": [128]}, "4096": {"baseline": [128], "obcache": [128]}}`. EOS로 작업량이 다르면 동일 작업량의 speedup으로 해석하지 않습니다.

latency는 로딩을 제외한 CLI `total:`이며, memory는 로딩·prefill을 포함한
프로세스 생애의 표본 최대다. Linux는 원본 mem_usage.sh로 모델 PID의 smaps RSS를
약 1초 sleep으로 읽고, Windows는 PSAPI current Working Set을 약 50ms sleep으로 읽었다.
API 조회·로그 기록 시간이 추가되며, 표본 사이의 순간 peak는 놓칠 수 있다.
OS peak는 별도 JSON에 보존했으며 주 지표와 혼용하지 않았다.
기존 helper의 보조 os_peak_rss_kib 필드는 CLI peak memory(RssAnon+accel)를 읽었다.
공개 JSON에서는 원본 로그의 Max Resident Set Size로 실제 OS peak를 재파싱하고,
기존 CLI 값과 원본 manifest를 별도로 보존했다. 주 latency·sampled RSS 수치는 변경하지 않았다.
CPU affinity는 Linux 0,2,4,6, Windows 미고정이다. 온도·주파수 제어는 하지 않았다.

K/V allocation 크기는 유지한다. Prefill 후 cache를 압축하고 decode 토큰을 추가하며,
추가 점수 계산과 CPU 구현 비용도 latency에 포함한다. 출력 품질은 이 성능 입력으로 판단하지 않는다.
**사용자 요청에 따라 LongBench는 실행하지 않았으며 품질 점수는 없다.**

Linux는 GCC 13.3.0, Windows는 MinGW GCC 13.2.0의 CPU release 빌드다.
테스트 옵션을 끈 별도 측정 빌드를 사용했다. 변경 없는 main core 라이브러리는 소스·헤더·
컴파일 옵션·툴체인 일치를 검증한 뒤 재사용했고, OBCache CausalLM 코드는 새로 빌드했다.
Windows는 baseline과 같은 task-local GNU 호환 설정 및 main-return exit adapter를 적용했다.
모델/지역 객체 정리와 main 반환 후 종료하며 DLL global destructor 구간은 제외한다.
전체 플랫폼 빌드 매트릭스 CI 통과를 주장하지 않는다.

Linux OBCache 12개(positive 6/negative 6)·기존 Qwen3 6개 모델 테스트와 KVCacheManager 20개 테스트가 통과했다.
양 OS의 작은 모델 off/zero/uncompressed/compressed 및 8-step decode 검사를 통과했다.
모든 본 측정의 raw 로그, activation marker, 실제 token 수, memory 표본과 hash를 재검증했다.
개별 trial, 표본 SD, 프로토콜, 소스·실행 파일·라이브러리 출처는 동명 JSON에 기록했다.
원본 로그와 빌드·검증 기록은 git에서 제외된 `build/validation/obcache-run/`에 보존했다.
